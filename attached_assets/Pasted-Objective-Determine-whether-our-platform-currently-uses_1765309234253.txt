Objective:
Determine whether our platform currently uses speculative decoding (a.k.a. draft-model verification acceleration).
If not, determine whether we should adopt it.
Base your reasoning on our existing codebase and architecture.

Tasks:
	1.	Inspect the codebase and identify:
	•	How inference is implemented.
	•	Whether we use:
	•	a draft model,
	•	KV-cache parallel verification,
	•	token-batch checking,
	•	or any speculative decoding pattern (OpenAI/Anthropic/Replit-style).
	•	Whether inference is compute-bound or memory-bound in our usage.
	2.	Determine whether our current inference runtime shows patterns that speculative decoding could improve, such as:
	•	slow sequential generation,
	•	large models (≥30B),
	•	memory bandwidth bottlenecks,
	•	high token-generation latency.
	3.	Compare our architecture to Replit’s approach:
	•	Do they use small-draft-model speculative decoding?
	•	Does our stack allow similar integration?
	•	What changes would be required?
	4.	If we are NOT using speculative decoding:
	•	Evaluate whether implementing it would yield:
	•	2–3× speedups,
	•	lower latency,
	•	lower GPU cost,
	•	better responsiveness.
	•	Identify constraints (model compatibility, infra, batching, KV cache access).
	5.	If we ARE using it:
	•	Assess whether our implementation is optimal compared to:
	•	OpenAI “SpecDec” 2023,
	•	Replit’s draft-model strategy,
	•	continuing improvements like multi-token prediction.
	6.	Output:
	•	A clear YES/NO on whether we currently use speculative decoding.
	•	A clear YES/NO on whether we should implement or improve it.
	•	Exact code locations and evidence supporting the answer.
	•	A recommended plan of action with estimated benefits.

Additional context from the user (to guide your evaluation):

Inference consists of two stages: fast parallel prefill + slow sequential generation.
Speculative decoding accelerates generation by replacing 5–7 sequential memory-bound steps with one parallel verification step.
Speedups of 2–3× are typical and lossless.
